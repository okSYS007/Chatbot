# Навыки и архитектура локального бота для публичной группы

## Цель

Сделать локального бота для публичной группы, которого админ запускает как приложение на своем компьютере. Первый этап: приветствие новых участников и система репутации по лайкам/реакциям. Проект должен быть готов к росту: сначала хранение в локальном файле, позже перенос на хостинг без переписывания логики с нуля.

Базовое предположение: группа в Telegram, а бот работает через Telegram Bot API. Если платформа другая, архитектура ниже все равно полезна, но интеграционный слой нужно заменить.

## Важное ограничение Telegram

Бот не может надежно восстановить все события за период, когда он не работал. Telegram хранит входящие updates ограниченное время, обычно до 24 часов. Значит:

- если бот был выключен ночью и включен утром, он сможет обработать события, которые еще лежат в очереди Telegram;
- если бот был выключен дольше срока хранения updates, часть вступлений, сообщений и реакций будет потеряна;
- бот не сможет сам получить полную историю реакций и вступлений задним числом через обычный Bot API;
- для надежной работы в будущем нужен хостинг, VPS, Docker, Windows service или другой способ держать процесс включенным постоянно.

Практический вывод: локальный режим подходит для MVP и маленькой группы, но репутация должна считаться только по событиям, которые бот реально видел.

## Язык ответов и правила команд

- Все ответы бота в Telegram должны быть на русском языке: ответы обычным пользователям, ответы админам, сообщения об ошибках и подсказки по использованию команд.
- Команды, доступные обычным пользователям, должны начинаться с `!`.
- Команды, доступные только администраторам, должны начинаться с `/`.
- Администраторам доступны оба типа команд: пользовательские `!` и админские `/`.
- Новые команды с префиксом `/` должны обязательно проверять права администратора перед выполнением.
- Новые публичные команды для обычных участников нельзя добавлять через `/`, чтобы не смешивать пользовательский и админский интерфейс.
- Белый список реакций, которые начисляют репутацию, хранится в `config.yaml` в `reputation.positive_reactions`.
- Если пользователь из `admins.user_ids` ставит реакцию из белого списка, автору сообщения начисляется репутация.
- Если пользователь из `admins.user_ids` убирает ранее засчитанную реакцию, начисленная за нее репутация откатывается.
- Для автоматической репутации важно только то, кто поставил реакцию: реакция должна быть поставлена админом из `admins.user_ids`.
- При запуске бот должен пытаться добавить администраторов Telegram-группы в `config.yaml` -> `admins.user_ids`, если Telegram API возвращает список админов.
- Админ-панель должна позволять вручную добавить Telegram user_id в `admins.user_ids`.
- Факты засчитанных реакций хранятся в `data/state.json`, чтобы бот мог отличить реальное начисление от обычной реакции и корректно сделать откат.

## Необходимые навыки бота

### 1. Интеграция с Telegram

Бот должен уметь:

- запускаться через long polling на локальном компьютере;
- принимать updates: сообщения, вступления участников, изменения состава группы, реакции;
- работать только в нужной группе по `chat_id`;
- игнорировать личные сообщения или отвечать в них только админскими подсказками;
- корректно сохранять `update_id`, чтобы не обрабатывать одно событие дважды;
- иметь настройку `allowed_updates`, включая сообщения, реакции и события участников.

Для приема событий о новых участниках бота лучше добавить в группу и выдать права администратора, иначе часть member updates может не приходить.

### 2. Конфигурация

Нужен отдельный файл настроек, например `config.yaml` или `config.json`.

Что хранить в настройках:

- токен бота из BotFather;
- `chat_id` группы;
- список ID админов бота;
- текст приветствия;
- путь к картинке приветствия, если она нужна;
- режим отправки приветствия: только текст, текст + картинка;
- список модераторов для репутации;
- веса реакций;
- правила антинакрутки;
- пороги активности пользователей.

Токен лучше хранить в `.env`, а не коммитить в репозиторий.

### 3. Хранилище данных

SQL на первом этапе не используем. Для локального MVP лучше выбрать один из двух вариантов:

1. JSON-файл на компьютере админа.

Это самый простой старт. Бот хранит состояние в `data/state.json`, а перед изменением делает резервную копию или атомарную запись через временный файл.

2. MongoDB на бесплатном тарифе.

Это хороший следующий шаг перед хостингом. Например, можно использовать MongoDB Atlas Free Tier. Тогда структура данных останется похожей на JSON, а перенос с локального файла будет проще, чем переход на SQL.

Для MVP рекомендуется начать с JSON, но сразу сделать отдельный слой `storage.py`, чтобы потом заменить JSON на MongoDB без переписывания логики бота.

Минимальная структура JSON:

```json
{
  "meta": {
    "last_update_id": 0,
    "started_at": null
  },
  "users": {
    "123456789": {
      "user_id": 123456789,
      "username": "example",
      "display_name": "User",
      "first_seen_at": "2026-05-26T12:00:00Z",
      "last_seen_at": "2026-05-26T12:00:00Z",
      "message_count": 0,
      "reputation": 10,
      "likes_received": 10,
      "likes_given": 3,
      "is_moderator": false,
      "is_blocked": false,
      "welcomed": true
    }
  },
  "rep_cooldowns": {
    "111111111:222222222": "2026-05-26T12:00:00Z"
  },
  "counted_reactions": {
    "chat_id:message_id:reactor_id:reaction": true
  },
  "pending_reactions": [],
  "settings": {}
}
```

Что важно: целые тексты сообщений не храним. Бот хранит только результат и технические ключи, которые нужны для защиты от повторного начисления.

Минимально нужно хранить:

- пользователя;
- количество сообщений;
- репутацию;
- количество засчитанных лайков;
- кто кому уже начислял репутацию и когда;
- какие реакции уже были учтены;
- последний обработанный `update_id`;
- факт, что пользователь уже получил приветствие.

Если позже понадобится аудит, можно добавить короткую историю последних начислений, но без текста сообщений.

### 4. Приветствие новых пользователей

Бот должен:

- ловить событие вступления пользователя;
- сохранять пользователя в базе;
- отправлять приветствие в группу;
- поддерживать шаблоны, например `{name}`, `{username}`, `{group}`;
- отправлять картинку, если путь к ней указан;
- не приветствовать одного и того же пользователя повторно при перезапуске;
- иметь команду админа для теста приветствия.

Пример шаблона:

```text
Привет, {name}! Добро пожаловать в группу.
```

Если бот был выключен, он сможет поприветствовать только тех новых участников, чьи updates еще доступны после запуска.

### 5. Учет активности

Для репутации важно понимать, кто является активным участником. Бот должен считать:

- количество сообщений пользователя;
- дату первого замеченного сообщения;
- дату вступления, если бот видел это событие;
- дату последней активности;
- количество дней с первого появления в базе.

Если бот не видел момент вступления, можно считать `first_seen_at` первым надежным моментом появления пользователя.

### 6. Система репутации

Рекомендованная модель для MVP: гибридная.

Репутация начисляется за положительную реакцию на сообщение, если выполняются условия:

- автор сообщения не является тем же пользователем, кто поставил реакцию;
- сообщение принадлежит целевой группе;
- реакция входит в список разрешенных, например 👍, ❤️, 🔥;
- реакция еще не была учтена для этой пары пользователей в рамках cooldown-периода;
- тот, кто ставит реакцию, считается доверенным или активным.

Такой вариант сочетает ваши идеи 2.1, 2.2 и 2.3.

Важно: чтобы узнать автора сообщения при реакции, бот должен либо видеть исходное сообщение в момент отправки, либо получить достаточно данных из события реакции. Если Telegram update не дает автора исходного сообщения, придется хранить минимальную связку `chat_id + message_id -> author_id`.

Это не хранение текста сообщения. Это только технический индекс:

```json
{
  "message_authors": {
    "chat_id:message_id": 123456789
  }
}
```

Индекс можно чистить по времени, например хранить только сообщения за последние 30-90 дней.

### 7. Роли в репутации

Стоит ввести 3 уровня доверия:

1. Модераторы

Модераторы находятся в белом списке. Их лайки всегда дают репутацию, если нет явной защиты от дублей.

2. Активные участники

Участник считается активным, если у него, например:

- минимум 20 сообщений в группе;
- или минимум 14 дней с момента первого появления/вступления;
- и нет ручной блокировки от админа.

3. Новички

Лайки новичков можно записывать в историю, но не начислять за них репутацию до тех пор, пока пользователь не станет активным.

### 8. Антинакрутка

Базовые правила:

- один пользователь не может начислить репутацию одному и тому же автору чаще одного раза за cooldown-период, например 7 дней;
- несколько реакций одного пользователя на одно сообщение считаются как одно событие;
- реакции автора на собственные сообщения не учитываются;
- реакции от заблокированных или слишком новых аккаунтов не учитываются;
- можно ввести дневной лимит начисления от одного пользователя, например максимум 5 репутационных лайков в сутки;
- можно ввести дневной лимит получения, например максимум 20 репутации в сутки от обычных участников.

### 9. Формула начисления

Простая формула для старта:

```text
+1 репутация за валидную положительную реакцию
+2 репутации, если реакцию поставил модератор
0 репутации, если реакция не прошла правила активности/cooldown
```

Позже можно добавить веса:

```text
👍 = +1
❤️ = +1
🔥 = +2
👎 = -1, если вы решите учитывать негативные реакции
```

Для начала лучше не учитывать негативные реакции, чтобы не открыть путь к токсичному минусованию.

### 10. Админ-команды

Нужны команды только для админов:

- `/rep @user` или `/rep_user user_id` - посмотреть репутацию;
- `/toprep` - топ участников по репутации;
- `/set_welcome` - изменить текст приветствия;
- `/test_welcome` - проверить приветствие;
- `/mod_add user_id` - добавить модератора репутации;
- `/mod_remove user_id` - убрать модератора;
- `/rep_add user_id amount reason` - ручное начисление;
- `/rep_sub user_id amount reason` - ручное списание;
- `/rep_history user_id` - история начислений;
- `/config` - показать основные настройки без токена.

### 11. Восстановление после запуска

При старте бот должен:

- загрузить конфиг;
- подключиться к базе;
- проверить миграции базы;
- загрузить последний обработанный update_id;
- запросить накопившиеся updates через long polling;
- обработать доступные события по порядку;
- не начислять репутацию повторно, если событие уже есть в базе;
- записать лог запуска и количество обработанных отложенных событий.

Если бот был выключен слишком долго, он должен записать предупреждение в лог: возможна потеря части событий.

### 12. Логи и диагностика

Нужны:

- файл логов `logs/bot.log`;
- понятные сообщения при ошибках Telegram API;
- лог начислений репутации;
- лог пропущенных реакций с причиной, например `cooldown`, `not_active`, `self_like`;
- команда админа `/health`, которая показывает состояние бота, базу, uptime и время последнего update.

### 14. Библиотеки Python

Для MVP:

- `python-telegram-bot` - работа с Telegram Bot API;
- `python-dotenv` - загрузка токена из `.env`;
- `PyYAML` - конфиг в YAML;
- `pydantic` - валидация настроек, если хочется строже;
- `pymongo` - только если сразу выбираем MongoDB;
- `pytest` - тесты логики репутации.

Логику репутации лучше писать отдельно от Telegram-хендлеров, чтобы ее можно было тестировать без реального бота.

### 15. Минимальный план разработки

1. Подготовить конфиг, `.env.example`, JSON-хранилище и структуру проекта.
2. Подключить Telegram long polling.
3. Добавить обработку новых участников и приветствие.
4. Добавить учет пользователей и сообщений.
5. Добавить обработку реакций.
6. Реализовать репутацию с cooldown, белым списком модераторов и порогами активности.
7. Добавить админ-команды для просмотра и ручной правки.
8. Покрыть тестами репутационную логику.
9. Подготовить режим переноса на хостинг: переменные окружения, понятный запуск, отсутствие абсолютных локальных путей.
10. Позже добавить MongoDB-хранилище тем же интерфейсом, что и JSON-хранилище.

### 16. Что лучше сделать в первом MVP

Для первой рабочей версии лучше не усложнять:

- приветствие: текст + опциональная картинка;
- репутация: `+1` от активного участника, `+2` от модератора;
- cooldown: 7 дней на пару `кто лайкнул -> кому лайкнул`;
- активность: 20 сообщений или 14 дней с первого появления;
- хранение: JSON-файл `data/state.json`;
- запуск: `python main.py`;
- админ-команды: `/toprep`, `/rep`, `/test_welcome`, `/health`.

Такой MVP уже будет полезен, но не загонит проект в тупик перед будущим хостингом.

## Открытые решения перед кодом

Перед реализацией нужно подтвердить:

- это точно Telegram-группа;
- какие реакции считать положительными;
- нужно ли учитывать негативные реакции;
- какой cooldown выбрать: 7 дней или другой срок;
- кто входит в белый список модераторов;
- приветствие должно отправляться в общий чат или в личку пользователю;
- нужно ли удалять приветствие через некоторое время;
- нужно ли показывать репутацию публично или только по команде.
- стартуем с JSON или сразу подключаем бесплатную MongoDB.

## Рекомендуемое решение по репутации

Я бы выбрал такой стартовый вариант:

```text
Репутация начисляется автору сообщения, когда другой пользователь ставит положительную реакцию.

Если реакцию поставил модератор: +2.
Если реакцию поставил активный участник: +1.
Если реакцию поставил новичок: событие сохраняется, но репутация не начисляется.

Один и тот же пользователь может начислить репутацию одному и тому же автору не чаще одного раза в 7 дней.
Самолайки не учитываются.
Негативные реакции на первом этапе не учитываются.
```

Это достаточно честно для маленькой группы, хорошо защищает от простых накруток и не требует сложной математики.
